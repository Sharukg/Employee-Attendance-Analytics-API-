# REVIEW.md

Review of the starter `app/main.py`. Everything below is fixed in the submitted `app/main.py`.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `MongoClient(...)` (top of file) | Client is not `tz_aware`, so PyMongo returns naive datetimes. They are later compared with aware IST datetimes or turned into JSON in an unknown zone. | `punch_out - punch_in` on stored records raises `can't subtract offset-naive and offset-aware datetimes`. | `MongoClient(..., tz_aware=True)`. All instants are UTC-aware. `to_ms()` and `to_dt()` convert at the API boundary. |
| 2 | `punch_in()`: `datetime.fromtimestamp(ms / 1000)` and `datetime.now()` | Uses the **server's local time zone** (R1 needs IST/UTC). Divides by 1000 as a float, so sub-second values are kept instead of being truncated to whole seconds. `if body.punched_at` treats `0` as "missing". | Run the server with `TZ=UTC` or `TZ=Asia/Kolkata`: the same `punched_at` produces a different `date`. `punched_at=…900 ms` is stored with milliseconds. | `to_dt(ms)` = `EPOCH + timedelta(seconds=ms // 1000)` (UTC, whole seconds). Check is `is not None`. |
| 3 | `punch_in()`: `d = ts.date().isoformat()` | The attendance date is the date in the server zone, not the IST date (R1). Overnight shifts are ignored. | Punch-in at 01:00 IST on 7 Jul gives 6 Jul in UTC. A 22:00-06:00 employee punching in at 05:30 IST gets the wrong day. | `attendance_date()` converts to IST and applies the overnight rule (punch-in earlier than `shift_end` belongs to the previous day). |
| 4 | `compute_late_minutes` | (a) `replace(hour, minute)` on the UTC value builds the shift start in the wrong zone and on the wrong day. (b) `int(x / 60) > 10` is wrong: 09:40:01 gives 10 min, which is not `> 10`, so it returns 0; R2 says it must be 10. (c) Float division. (d) Ignores overnight shifts. | `09:40:01` on a 09:30 shift returns 0 (expected 10). On a UTC server every punch is hours "late" or "early". | Shift start is built in IST for the attendance date. Compare **seconds** (`> 600`), then floor to minutes. |
| 5 | `compute_work_hours` | Python `round()` is banker's rounding on a float (R4 wants half-up). `round(8.125, 2)` gives 8.12 and `round(0.125, 2)` gives 0.12. | Punch-in 09:00:00, punch-out 17:07:30 gives 8.125 h; expected 8.13. | `Decimal(seconds) / 3600` quantized with `ROUND_HALF_UP`. |
| 6 | `compute_overtime` | No 30-minute minimum (R3). Always uses the *same* calendar day as `shift_end`, so overnight shifts get a wildly wrong value. Uses `int()` of a float. | Out at 18:45 on a 18:30 shift gives 15 (expected 0). Overnight 22:00-06:00 (date 6 Jul), out 06:40 on 7 Jul gives 1480 (expected 40). | `shift_end_at()` adds one day for overnight shifts. Floor minutes, returned only if `>= 30`. |
| 7 | `create_employee`: `find_one` then `insert_one` | Check-then-insert race: two parallel creates can both pass the check. There is no unique index. | 20 parallel POSTs of the same `emp_code` produce more than one 201. | Unique index on `emp_code`; `DuplicateKeyError` becomes 409. |
| 8 | `EmployeeIn` | No validation at all: any `emp_code`, bad e-mail, `joined_on="banana"`, `shift_start == shift_end`, `09:61`, empty or giant strings. | `POST joined_on=2026-02-30` returns 201 and later breaks the analytics. | Pydantic patterns and lengths from the contract, a real-date check for `joined_on`, and `shift_start != shift_end`. |
| 9 | `create_employee` response | Returns `created_at` as a naive local `datetime` (serialised as an ISO string). The contract says epoch milliseconds, and the stored value is local, not UTC. | The response has `"created_at": "2026-10-12T11:42:00.123"`. | Store a UTC datetime, return `to_ms()`. A shared `employee_out()` builds the response. |
| 10 | `list_employees`: `skip = page * page_size` | Off by one page: page 1 skips the first page. `total` counts the whole collection, not the filter. No sort, so the order is arbitrary. `page=0` gives a negative skip (500). `page_size` is unbounded. | `GET /employees?page=1` misses the first 20 employees. `?department=Ops` reports the total for everyone. | `(page-1) * page_size`, `count_documents(filter)`, `sort emp_code`, `page >= 1`, `1 <= page_size <= 100` (422 otherwise). |
| 11 | `punch_in`: `emp = find_one(...)` | An unknown employee gives `emp is None`, so `emp["shift_start"]` raises `TypeError` (500). Contract says 404. | `POST /attendance/punch-in {"emp_code": "NOPE"}`. | `get_employee()` raises 404. |
| 12 | `punch_in`: `status` is a free string | `ABSENT`, `LEAVE` or `"banana"` are accepted. They would be stored with a punch-in. `punched_at` accepts seconds, floats and out-of-range values. | `{"status": "ABSENT"}` returns 201. `punched_at: 1783312500` (seconds) is accepted and lands in 1970. | `Literal["PRESENT","WFH","ON_DUTY"]`. `punched_at` is a strict int in `[1e11, 4102444800000]`, so seconds, floats and strings are 422. |
| 13 | `punch_in`: `find_one` then `insert_one` | Check-then-insert race. Two simultaneous punch-ins both pass the check and both insert. | 10 parallel identical requests give several 201s. | Unique index `(emp_code, date)`. The loser's `DuplicateKeyError` becomes 409. Exactly one insert wins. |
| 14 | `punch_in` response | Returns an `id` (the ObjectId as a string), which the contract forbids. `punch_in` is a raw datetime, not epoch ms. Seeded records may lack fields. | The response has `"id"` and `"punch_in": "2026-07-06T10:05:00"`. | `record_out()` builds the response: no `_id`, epoch ms, defaults for missing fields, `history` mapped. |
| 15 | `list_attendance` | Loads **every matching document** into memory and sorts and slices in Python. The sort is only by `date` desc (no `emp_code` tie-break; Python's sort is stable, so ties follow storage order). No indexes. Returns `id`. | With 100k documents each call takes seconds and a lot of memory. Same-date rows are not ordered by `emp_code`. | Server-side `find(...).sort(date desc, emp_code asc).skip().limit()` backed by an index. `total` from `count_documents` (or `estimated_document_count` when unfiltered). |
| 16 | `list_attendance` parameters | `date_from > date_to` is not rejected, `date_from="abc"` is not rejected (it silently matches nothing), `status` and `page`/`page_size` are not validated (`page=0` makes a negative slice index). | `?date_from=2026-07-31&date_to=2026-07-01` returns 200 with an empty page. | `parse_date()` (strict `YYYY-MM-DD` and a real date), `date_from <= date_to`, `Literal` status, bounded page values: all 422. |
| 17 | `/health` | Always returns `ok`, even if MongoDB is down. The contract needs 503. | Stop MongoDB and call `/health`: still 200. | `client.admin.command("ping")`, 503 on `PyMongoError`. |
| 18 | Startup | No index is created. Every query in the starter is a collection scan. Client has the default 30 s server-selection timeout. | `explain` shows `COLLSCAN`. A request to a dead DB hangs 30 s. | `ensure_indexes()` in the app lifespan (idempotent, fixed names, retried a few times). `serverSelectionTimeoutMS=5000`. |

**Examined and judged fine (kept):**
- `load_dotenv()` does not override real environment variables, so the injected `MONGO_URI`/`MONGO_DB` win, as the contract requires. I kept the `localhost` fallback only for local convenience.
- A synchronous PyMongo client inside plain `def` endpoints is fine here: FastAPI runs them in a thread pool, and `MongoClient` is thread-safe with its own connection pool.
- `doc.pop("_id")` after `insert_one`: correct (insert_one adds `_id`), but I replaced it with explicit response builders so `_id` can never leak.
- `IST = timezone(timedelta(hours=5, minutes=30))` is correct (IST has no DST).
- Default shift times `09:30`/`18:30` match the contract.
